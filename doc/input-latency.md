# 鼠标输入延迟诊断

## 当前改动

- 客户端每批最多处理 64 条消息，或在处理完一条消息后发现已耗时 2 ms 时结束该批。
  每批结束立即刷新合并的移动；剩余完整消息通过后续事件继续处理。
  这是协作式预算，单条消息及平台调用仍可能超过 2 ms。
- 服务端在事件队列下一次刷新前合并连续移动：绝对坐标保留最新值，
  相对坐标累加。切换移动类型或发送任何其他协议消息前先刷新移动。
  相对累加超出协议的有符号 16 位范围前提前发送。
- 不设置固定等待定时器，但排队刷新仍可能增加一个事件队列周转的延迟。
  此优化减少队列内连续移动的重复发送，不能消除已进入 TCP/系统缓冲的数据积压。

## 启用统计

统计默认关闭。完全退出已有进程，再从设置了环境变量的终端启动编译后的程序。
Windows GUI 启动的服务进程不一定继承终端环境；诊断时建议直接启动服务端命令行程序。

Windows PowerShell，使用实际编译产物路径和原来的服务器配置：

```powershell
$env:INPUTLEAP_INPUT_STATS = '1'
& '你的构建目录\bin\Release\input-leaps.exe' --no-daemon --debug INFO --config '你的服务器配置路径'
```

Linux，使用当前 Windows 的内网 IP：

```bash
INPUTLEAP_INPUT_STATS=1 ./build/bin/input-leapc --no-daemon --debug INFO <Windows_IP>
```

每项指标在收到样本且距离上次输出至少 5 秒时输出 `input-stats` 汇总。
停止移动后不足一个输出周期的尾部样本不会单独输出。日志为每个连接对象各自统计。

- `send-mouse-wait`：发送端从首个待合并移动入队到提交协议消息的耗时。
- `send-mouse-merged`：每次发送包含的原始移动事件数；1 表示没有合并。
- `tcp-output-buffer`：每次追加数据后的应用层 TCP 输出缓冲字节数，包括非输入数据。
- `tcp-output-busy-age`：成功写出数据时，本轮缓冲从空变为非空后已持续的时间；
  不是单个事件的网络延迟，也不包括内核发送缓冲。
- `receive-batch` / `receive-batch-size`：客户端一批处理耗时和消息数。
- `mouse-injection-call`：客户端调用平台注入方法的耗时，不包括桌面合成器实际显示时间。

这些是本地耗时和积压指标，不能直接测出两机间单向延迟或鼠标到画面的完整延迟。
对照测试使用相同 Wi-Fi、回报率、屏幕刷新率和日志级别；在 Linux 实体屏幕观察。
新版 Windows 服务端与 Linux 客户端都需要重新编译和启动，才能覆盖两端优化。

## 验证

有 GCC 的 Linux/WSL 环境中执行：

```bash
bash src/test/standalone/check-input-latency.sh
```

该检查对四个修改后的实现文件做 Linux 语法检查，并直接链接实际发送端和协议序列化实现，
验证绝对坐标合并、相对位移累计及溢出、点击/按键/滚轮顺序、移动类型切换、
显式 flush、关闭和销毁后遗留事件处理。它不替代完整构建、客户端事件循环测试或真机测试。
